LEO OPUS is a production cross-platform mobile ecosystem engineered using Flutter and Dart, backed by Cloud Firestore, Firebase Authentication, Firebase Storage, and a dedicated Node.js/Express.js micro-backend. Q3: What was the single most challenging technical problem you solved in this project?

  • Interviewer Focus: Tests problem-solving ability, debugging methodologies, resilience, and root-cause analysis.
  • Answer A (Concise):
The most challenging problem was an asynchronous race condition during user registration and authentication, where newly registered users experienced permission-denied crashes upon redirect. The Firebase Auth user was created instantly, but the corresponding Firestore user role document was still being committed over the network. I resolved this by designing an in-memory session cache paired with an exponential retry loop with backoff in _getUserRole, ensuring zero failed logins.
  • Answer B (Technical Deep-Dive):
This issue involved a timing conflict across three distinct asynchronous layers: 1. The Root Cause: In _MainAppContent in [lib/main.dart](file:///d:/Shinnovation/leox/lib/main.dart#L174-L281), FirebaseAuth.instance.authStateChanges() triggered immediately after createUserWithEmailAndPassword() succeeded. The router attempted to fetch the user's role from /users/{uid} in Firestore. However, because Firestore writes are asynchronous network operations, the document did not exist yet, causing _getUserRole() to return null and sign the user out immediately. 2. Security Rule Mismatch: Furthermore, our security rules originally checked get(/databases/$(database)/documents/users/$(request.auth.uid)).data.role == 'employer', but our auth provider had saved the document to /employers/{uid}, resulting in a FirebaseException: PERMISSION_DENIED. 3. The Solution: - First, in [SessionService](file:///d:/Shinnovation/leox/lib/services/session_service.dart), I created a targetRole cache that records the user's intended role in-memory prior to triggering auth. - Second, in _getUserRole, I implemented a retry mechanism (10 attempts with 2-second delays) with cascading fallback checks querying /users, /employers, /employees, /mc_providers, and /mc_seekers. - Third, I updated firestore.rules so isEmployer() checks both the users collection and the employers collection (exists(...)). - Finally, I verified the fix with unit and integration tests.
  • Verified Evidence: Documented in [FIXES_NEEDED.md](file:///d:/Shinnovation/leox/FIXES_NEEDED.md); implemented in [lib/main.dart](file:///d:/Shinnovation/leox/lib/main.dart#L319-L418) and [firestore.rules](file:///d:/Shinnovation/leox/firestore.rules#L18-L23).

📱 Deep Dive: Flutter Framework Architecture

Flutter is not a native wrapper (like Cordova or React Native via bridge); it renders directly to the canvas using a compiled C++ engine (Impeller / Skia). Understanding its internal three-tree rendering pipeline is essential for senior technical and fresher interviews alike.

The Three Trees in Flutter

1. Widget Tree: An immutable blueprint or configuration of the UI. When state changes, widgets are created and discarded cheaply in memory. 2. Element Tree: The persistent skeletal structure that manages the lifecycle of widgets and coordinates updates. An Element holds a reference to both its Widget and its corresponding RenderObject. BuildContext is literally the Element corresponding to that widget. 3. RenderObject Tree: The mutable visual layout and paint engine. Responsible for measuring constraints, calculating layout dimensions, hit-testing touch events, and painting pixels.

Q6: What is the difference between StatelessWidget and StatefulWidget, and when do you use each?

  • Interviewer Focus: Tests understanding of widget immutability, state lifecycle, and memory implications.
  • Answer A (Concise):
A StatelessWidget is an immutable configuration whose visual representation depends solely on configuration parameters passed into its constructor and inherited context; its build() method produces the same UI every time unless rebuilt by an external parent or provider. A StatefulWidget maintains a persistent, mutable State object across widget rebuilds, used when a widget must internally track changing data over time (such as text input, animations, or controller lifecycles).
  • Answer B (Technical Deep-Dive):
- StatelessWidget: Implements only build(BuildContext context). The framework instantiates a StatelessElement that calls build() once during layout. It is lightweight because it holds no long-lived state. In LEO OPUS, we use StatelessWidget for pure visual presenters, such as [StatCard](file:///d:/Shinnovation/leox/lib/widgets/stat_card.dart) and [SubscriptionGate](file:///d:/Shinnovation/leox/lib/widgets/subscription_gate.dart#L7-L25). - StatefulWidget: Overrides createState() returning a persistent State object. The framework instantiates a StatefulElement that holds the State instance across multiple rebuild cycles. When the parent widget rebuilds with new properties, didUpdateWidget() is invoked without discarding the underlying State object. In LEO OPUS, we use StatefulWidget in screens managing controllers and native SDKs, such as [PremiumPaywall](file:///d:/Shinnovation/leox/lib/widgets/premium_paywall.dart#L10-L77), which initializes Razorpay, registers event callbacks, and disposes text controllers in dispose().
  • Verified Evidence:
- StatelessWidget: [SubscriptionGate](file:///d:/Shinnovation/leox/lib/widgets/subscription_gate.dart#L7) - StatefulWidget: [PremiumPaywall](file:///d:/Shinnovation/leox/lib/widgets/premium_paywall.dart#L10), [_MainAppContent](file:///d:/Shinnovation/leox/lib/main.dart#L118)

  • Follow-up Answer: "Yes! If a StatelessWidget subscribes to an InheritedWidget (e.g., via context.watch() or Consumer), when that InheritedWidget notifies its dependents, the framework marks that StatelessElement as dirty and re-executes its build() method."

Q7: Explain the lifecycle of a StatefulWidget. Where and why do you use each lifecycle method in LEO OPUS?

  • Interviewer Focus: Assesses lifecycle management, resource cleanup, and avoiding memory leaks.
  • Answer A (Concise):
A StatefulWidget lifecycle starts with createState(), followed by initState() for one-time initialization, didChangeDependencies() when inherited widgets change, build() for rendering, didUpdateWidget() when parent properties change, deactivate() when temporarily removed from the tree, and finally dispose() to release memory, cancel streams, and clean up controllers.
  • Answer B (Technical Deep-Dive):
Here is how the lifecycle executes sequentially, mapped directly to LEO OPUS code: 1. createState(): Framework creates the persistent State instance. 2. initState(): Called exactly once when the element is inserted into the tree. - LEO OPUS Usage: In [PremiumPaywall](file:///d:/Shinnovation/leox/lib/widgets/premium_paywall.dart#L65-L70), we instantiate the native Razorpay instance and register event handlers: _razorpay.on(Razorpay.EVENT_PAYMENT_SUCCESS, _handlePaymentSuccess). - Post-Frame Callbacks: If we need to trigger asynchronous provider loading, we use WidgetsBinding.instance.addPostFrameCallback((_) { ... }) inside initState() (as in [_EmployeeAiResumeMatcherViewBodyState](file:///d:/Shinnovation/leox/lib/views/employee/employee_ai_resume_matcher.dart#L38-L43)), avoiding calling notifyListeners() during the active build phase. 3. didChangeDependencies(): Triggered immediately after initState() and whenever an InheritedWidget that this state depends on updates. Ideal for Theme.of(context) or MediaQuery.of(context) calculations. 4. build(BuildContext context): Pure layout generation function. Called repeatedly whenever setState() is called or inherited dependencies change. Must be kept synchronous and fast. 5. didUpdateWidget(covariant T oldWidget): Triggered when the parent rebuilds and provides new constructor arguments with the same runtime type and key. 6. deactivate(): Triggered when the element is removed from the tree (e.g., during navigation push/pop). 7. dispose(): Permanent destruction of the state object. - LEO OPUS Usage: In [PremiumPaywall](file:///d:/Shinnovation/leox/lib/widgets/premium_paywall.dart#L72-L77), we call _razorpay.clear() and _couponController.dispose().   • Likely Follow-up: "Why should you never call an asynchronous function or notifyListeners() directly inside build()?"
  • Follow-up Answer: "Because build() must be a synchronous, deterministic function with zero side effects. Triggering state mutations inside build() schedules another build while the current frame is rendering, throwing a 'setState() or markNeedsBuild() called during build' exception."

Q8: What is BuildContext, and why is it so important in Flutter?

  • Interviewer Focus: Core conceptual understanding of Flutter's element tree and widget ancestry.
  • Answer A (Concise):
BuildContext is a handle to the location of a widget within the global element tree. It gives the widget access to its parent hierarchy, enabling it to locate ancestor widgets, look up themes, access Navigator for screen transitions, and read dependency-injected providers.
  • Answer B (Technical Deep-Dive):
Internally in Flutter's source code, BuildContext is an abstract interface implemented directly by Element. When a widget's build(BuildContext context) method runs, the context passed in is literally the Element corresponding to that widget. Key responsibilities of BuildContext in LEO OPUS: 1. Q11: How does Dart's asynchronous execution model work (Event Loop, Microtasks, Futures, and Streams)?

  • Interviewer Focus: Assesses understanding of single-threaded concurrency, event queues, and non-blocking I/O.
  • Answer A (Concise):
Dart is single-threaded and executes within an Isolate. It handles asynchronous concurrency via an Event Loop that continuously pulls tasks from two FIFO queues: the high-priority Microtask Queue (internal scheduling) and the Event Queue (I/O, timers, user touch events, network responses). A Future represents a potential value or error that will complete in the event queue, while a Stream represents an asynchronous sequence of multiple events over time.
  • Answer B (Technical Deep-Dive):
The Dart Event Loop Architecture: - Dart code runs inside an Isolate containing its own memory heap and single execution thread. - The Event Loop operates as: 
    while (true) {
      if (microtaskQueue.isNotEmpty) {
        execute(microtaskQueue.dequeue());
      } else if (eventQueue.isNotEmpty) {
        execute(eventQueue.dequeue());
      }
    }
- Futures vs Streams in LEO OPUS: - Future: Used for one-time operations. For example, [ApiService.post](file:///d:/Shinnovation/leox/lib/services/api_service.dart#L79) initiates an HTTP request, yielding control back to the event loop. When the OS network socket returns data, the future's completion callback is enqueued on the Event Queue. - Stream: Used for continuous real-time data flows. For example, [FirebaseFirestore.instance.collection('jobs').snapshots()](file:///d:/Shinnovation/leox/lib/providers/employer_jobs_provider.dart#L46) returns a Stream.   • Follow-up Answer: "An async function still runs on the main thread; it only yields execution when waiting for asynchronous I/O (like network or disk operations). Q20: Explain the Compound Indexes you created in Firestore. Why were they necessary, and how did they reduce query time by 60%?

  • Interviewer Focus: Query optimization, B-tree indexes, distributed database query execution, and performance benchmarking.
  • Answer A (Concise):
By default, Firestore automatically creates single-field indexes for every field. However, compound queries that filter on one field (e.g., where('postedBy', isEqualTo: uid)) and sort on a different field (e.g., orderBy('postedOn', descending: true)) require composite indexes. Without compound indexes, Firestore either rejects the query or forces the client to download all records and sort in memory. By defining composite indexes in firestore.indexes.json, the database engine navigates a pre-sorted multi-dimensional index tree, reducing query retrieval times by 60%.
  • Answer B (Technical Deep-Dive):
In [firestore.indexes.json](file:///d:/Shinnovation/leox/firestore.indexes.json#L1-L60), we defined four critical compound indexes: 1. jobs: postedBy (ASCENDING) + postedOn (DESCENDING) — Used in [EmployerJobsProvider.loadJobs](file:///d:/Shinnovation/leox/lib/providers/employer_jobs_provider.dart#L48). 2. jobs: status (ASCENDING) + postedOn (DESCENDING) — Used in [EmployeeJobsProvider](file:///d:/Shinnovation/leox/lib/providers/employee_providers/employee_jobs_provider.dart) to show 'Open' jobs sorted by most recent. 3. applications: employeeId (ASCENDING) + appliedAt (DESCENDING) — Used in [MyApplicationsView](file:///d:/Shinnovation/leox/lib/views/employee/my_applications_view.dart) for candidates to track application histories chronologically. 4. applications: jobId (ASCENDING) + appliedAt (DESCENDING) — Used in [CandidatesView](file:///d:/Shinnovation/leox/lib/views/employer/candidates_view.dart) for employers to review applicant queues chronologically. On mobile devices with 500+ records, network transfer and memory allocation caused noticeable 400–800ms UI freezes. - With Compound B-Tree Index: Firestore server traverses pre-sorted composite index entries in $O(\log K)$ time (where $K$ is the indexed subset), transfers only the top paginated results, and streams them directly into the widget tree in under 150ms.
  • Verified Evidence: firestore.indexes.json lines 1–60; Akash_Sanjay_More_Resume.md line 42.

📚 Core DSA Technical Interview Revision

Arrays & Strings

  • Key Concepts: Contiguous memory allocation, cache locality, amortized $O(1)$ dynamic array resizing, two-pointer techniques, sliding window.
  • Project Application: Resume skill array deduplication: converting List to Set in $O(N)$ time.
  • Typical Interview Question: "How does a dynamic array double its capacity, and why is insertion amortized $O(1)$?"
- Answer: When the underlying array fills up, a new array of size $2N$ is allocated in memory and all $N$ elements are copied over ($O(N)$ cost). However, since this doubling only occurs after $N$ insertions, the total cost for $N$ insertions is $N + N/2 + N/4 + \dots = 2N$. Spreading $2N$ across $N$ insertions yields an amortized time of $O(1)$ per insertion.

Hash Tables & Hash Maps

  • Key Concepts: Hash functions, collision resolution (separate chaining vs open addressing with linear/quadratic probing), load factor (typically 0.75), rehashing.
  • Project Application: SessionService in-memory key-value lookups; Firestore document field mapping via Dart Map ($O(1)$ average lookup and insertion).
  • Typical Interview Question: "What happens when two keys hash to the same index in a hash map?"
- Answer: A hash collision occurs. In separate chaining, entries at that bucket index are stored in a linked list or self-balancing Red-Black tree (as in Java 8+ when bucket length exceeds 8). In open addressing, the algorithm probes adjacent slots until an empty slot is found.

Stacks & Queues

  • Key Concepts: LIFO (Last In First Out) vs FIFO (First In First Out), monotonic stacks, circular queues, deque.
  • Project Application: Flutter's Navigator operates as a route stack (push adds a route to the top; pop removes the top route; popUntil unwinds the stack to the root route). Express background rate-limit queueing (pending_matches).
  • Typical Interview Question: "How would you implement a Queue using two Stacks?"
- Answer: Use stackIn and stackOut. Enqueue pushes onto stackIn in $O(1)$. Dequeue checks stackOut; if empty, it pops all elements from stackIn and pushes them onto stackOut, reversing their order. Popping from stackOut yields FIFO order in amortized $O(1)$ time.

Linked Lists

  • Key Concepts: Singly vs doubly linked lists, pointer manipulation, detecting cycles (Floyd's Tortoise and Hare algorithm), reversing in-place.
  • Project Application: In Dart's event loop, microtask and event queues are internally implemented as linked node queues.
  • Typical Interview Question: "How do you detect a cycle in a linked list in $O(N)$ time and $O(1)$ memory?"
- Answer: Use Floyd's Cycle Detection algorithm with two pointers: a slow pointer moving 1 step at a time and a fast pointer moving 2 steps. If a cycle exists, the fast pointer will eventually lap and meet the slow pointer. If fast or fast.next reaches null, the list has no cycle.

Trees & Binary Search Trees (BST)

  • Key Concepts: Tree traversals (Inorder, Preorder, Postorder, Level-order/BFS), BST invariants (Left < Root < Right), AVL Trees & Red-Black Trees (self-balancing with height $O(\log N)$), B-Trees.
  • Project Application: Cloud Firestore uses distributed B-Trees to index fields, enabling compound range and equality queries in $O(\log N)$ disk seek time. Flutter's Widget Tree and RenderObject Tree.
  • Typical Interview Question: "Why do databases like MySQL and Firestore use B-Trees instead of Binary Search Trees for indexes?"
- Answer: Binary Search Trees have at most 2 children per node, resulting in deep trees that require many disk I/O operations. B-Trees have a high branching factor ($M$ children per node), meaning tree height is shallow (typically 3–4 levels for millions of rows), minimizing disk head seeks.

Graphs & Traversal Algorithms

  • Key Concepts: Graph representations (Adjacency Matrix $O(V^2)$ vs Adjacency List $O(V+E)$), Breadth-First Search (BFS via Queue), Depth-First Search (DFS via Stack/Recursion), Dijkstra's Shortest Path, Topological Sort.
  • Project Application: Flutter's Element Tree layout and render pipeline performs Depth-First traversal during the layout pass to measure constraints from parent to child, and synthesizes sizes from child to parent.
  • Typical Interview Question: "What is the time complexity of BFS and DFS on an adjacency list?"
- Answer: Both BFS and DFS run in $O(V + E)$ time, where $V$ is the number of vertices and $E$ is the number of edges, because each vertex is visited once and each edge is examined once.

Q24: What is the difference between a Process and a Thread? How does this apply to Flutter on Android?

  • Interviewer Focus: OS process model, thread scheduling, memory address spaces, and Flutter threading.
  • Answer A (Concise):
A Process is an independent executing program with its own dedicated virtual address space, memory heap, file descriptors, and security sandbox allocated by the OS. Q25: Explain Deadlock, its Four Necessary Conditions (Coffman Conditions), and how they are prevented in software design.

  • Interviewer Focus: Concurrency theory, synchronization bugs, race conditions, and Coffman's conditions.
  • Answer A (Concise):
A Deadlock occurs when a set of concurrent processes or threads are permanently blocked because each is holding a resource and waiting for another resource held by another process in the set. For a deadlock to occur, all four Coffman conditions must hold simultaneously: Mutual Exclusion, Hold and Wait, No Preemption, and Circular Wait. Deadlocks are eliminated by breaking at least one of these conditions, most commonly by enforcing strict lock acquisition ordering to eliminate Circular Wait.
  • Answer B (Technical Deep-Dive):
The Four Coffman Conditions: 1. Mutual Exclusion: At least one resource must be held in a non-shareable mode (only one thread can use it at a time). 2. Hold and Wait: A thread must be holding at least one resource and waiting to acquire additional resources held by other threads. 3. No Preemption: Resources cannot be forcibly confiscated from a thread; they can only be released voluntarily after the thread completes its task. 4. Circular Wait: A closed chain of threads exists such that $T_1$ waits for a resource held by $T_2$, $T_2$ waits for $T_3$, and $T_n$ waits for $T_1$. How to Break Deadlocks in System Design: - Eliminate Circular Wait: Enforce a global resource hierarchy. If thread A needs Lock 1 and Lock 2, and thread B needs both, both threads must acquire Lock 1 before Lock 2. - Eliminate Hold and Wait: Require threads to request all required resources simultaneously upfront, or release held locks before requesting new ones. - Database Deadlock Handling: In Cloud Firestore and relational databases, transactions detect deadlocks using wait-for graphs and resolve them by aborting and rolling back one transaction (breaking No Preemption) with exponential backoff.
  • Verified Evidence: Handled in backend concurrency in backend/routes/subscription.js.
  • Likely Follow-up: "Does Dart experience classical multi-threaded deadlocks on its main thread?"
  • Follow-up Answer: "No! Because Dart's main isolate is single-threaded and executes non-preemptively via an event loop, classical thread lock deadlocks cannot occur in standard Dart code. However, logical deadlocks can occur if two asynchronous Futures are waiting on each other's completion (Completer) circularly."
  • Common Mistakes to Avoid: Always name the four Coffman conditions precisely: Mutual Exclusion, Hold & Wait, No Preemption, Circular Wait.

Q27: What is the difference between HTTP and HTTPS? Explain the TLS Handshake.

  • Interviewer Focus: Cryptography, public key infrastructure (PKI), TLS handshake, and transport layer security.
  • Answer A (Concise):
HTTP transmits data in clear plaintext over TCP port 80, leaving it vulnerable to eavesdropping, packet sniffing, and man-in-the-middle (MITM) attacks. HTTPS encrypts traffic using TLS (Transport Layer Security) over port 443, ensuring confidentiality (symmetric encryption), integrity (cryptographic hashing), and server authenticity (X.509 digital certificates signed by trusted Certificate Authorities).
  • Answer B (Technical Deep-Dive):
The TLS 1.3 Handshake Sequence: 1. Client Hello: Mobile client connects to leox-kfsm.onrender.com over TCP and sends supported cipher suites, TLS version (TLS 1.3), and a client random string + Diffie-Hellman public key share. 2. Server Hello & Certificate: Server selects cipher suite, sends its Diffie-Hellman public key share, server random string, and its X.509 SSL Certificate issued by a Certificate Authority (Let's Encrypt / Google Trust Services). 3. Authentication & Key Exchange: Mobile client verifies the server certificate against the root CA certificates embedded in the mobile operating system (Android/iOS trust store). Both parties independently calculate the shared symmetric Master Secret using Diffie-Hellman math. 4. Encrypted Communication: All subsequent HTTP traffic (Bearer tokens, resume text, Razorpay signatures) is encrypted using symmetric AES-256-GCM or ChaCha20-Poly1305, which is fast and secure.

Q33: Why must payment signatures be verified on the server using HMAC SHA-256 instead of trusting the mobile callback?

  • Interviewer Focus: Financial transaction security, man-in-the-middle attacks, client-side tampering, and cryptography.
  • Answer A (Concise):
Mobile clients run on user-controlled hardware. A malicious user with a rooted phone, proxy tool (like Charles or Burp Suite), or decompiled APK can intercept network traffic or modify local memory to fake a successful payment response. By verifying the HMAC SHA-256 signature on our Node.js server using our private RAZORPAY_KEY_SECRET, we prove mathematically that the payment confirmation was generated by Razorpay's servers and that the payment details have not been altered.
  • Answer B (Technical Deep-Dive):
In [backend/routes/subscription.js](file:///d:/Shinnovation/leox/backend/routes/subscription.js#L303-L314): 
  const generated_signature = crypto
    .createHmac('sha256', keySecret)
    .update(razorpayOrderId + '|' + razorpayPaymentId)
    .digest('hex');


if (generated_signature !== razorpaySignature) {
    console.warn('[VerifyPayment] Invalid Razorpay signature detected');
    return res.status(400).json({ success: false, error: 'Signature verification failed. Potential tampering.' });
  }

How HMAC-SHA256 Works:
1. When a user pays on Razorpay's gateway, Razorpay computes a keyed-hash message authentication code (HMAC) by hashing the concatenated string order_id + '|' + payment_id using the secret key shared between Razorpay and our server.
2. The mobile app receives this signature and transmits it to our server.
3. Our server computes the exact same hash using our secret key.
4. Because the secret key is NEVER exposed to the mobile app or browser, an attacker cannot forge a valid signature for an unpaid order ID. If an attacker tampers with the payment ID or attempts to activate an order without paying, the computed hash will not match, and the request is rejected with HTTP 400.
  • Verified Evidence: backend/routes/subscription.js lines 303–314; lib/widgets/premium_paywall.dart lines 91–100.

  • Likely Follow-up: "What is the difference between Test Mode and Live Mode in Razorpay?"

  • Follow-up Answer: "In Test Mode (rzp_test_xxx), transactions use simulated mock banking rails without real money movement. In Live Mode (rzp_live_xxx), transactions process real currency via banking networks. In our backend code (line 268), we explicitly block simulated payment bypasses if live keys are active (cleanKeyId.startsWith('rzp_live_'))."

  • Common Mistakes to Avoid: Never assume that receiving a callback on the mobile client is sufficient proof of payment. Always state that server-side cryptographic signature verification is mandatory.

🛠️ 13 Realistic Debugging Case Studies

Scenario 1: User Registration Fails with "PERMISSION_DENIED" in Firestore

  • Symptoms: User completes registration, but immediately crashes or gets redirected back to the login screen with a permission error.
  • Possible Causes: Firestore security rules check /users/{uid}, but registration wrote to /employers/{uid}; or asynchronous network latency caused the role document write to lag behind auth state changes.
  • Diagnostic Approach A (Console & Rules): Inspect Firebase Console Firestore tab to check if /users/{uid} exists. Review firestore.rules simulator with the user's auth token.
  • Diagnostic Approach B (Code & Logs): Trace _getUserRole in lib/main.dart. Check debug logs for "Registry Check (users/$uid): exists=false".
  • Root Cause Isolation: Asynchronous race condition: FirebaseAuth.instance.authStateChanges() fired before Firestore finished writing the profile document.
  • Fix: Implemented an in-memory targetRole cache in SessionService and added a 10-attempt retry loop with 2-second backoff in _getUserRole (lib/main.dart lines 319–407). Updated firestore.rules so isEmployer() checks both users and employers.
  • Regression Test: Write an integration test that logs in immediately after registration and asserts that _getUserRole returns a non-null role within 3 retries.
  • Prevention: Always decouple auth creation from profile hydration using optimistic client caching or serverless cloud function triggers.

Scenario 2: Node.js Backend Returns HTTP 500 on Payment Signature Verification

  • Symptoms: Mobile checkout succeeds on Razorpay, but the app shows "Verification Failed" and the subscription remains inactive.
  • Possible Causes: Secret key mismatch between .env and Razorpay Dashboard; malformed payload missing razorpaySignature; surrounding quotes in .env variable values.
  • Diagnostic Approach A (Server Logs): Check Render server logs: [VerifyPayment] Invalid Razorpay signature detected. Compare computed HMAC against received signature.
  • Diagnostic Approach B (Code Inspection): Check cleanKeySecret helper in backend/routes/subscription.js line 10.
  • Root Cause Isolation: Surrounding quotes inside .env (e.g., RAZORPAY_KEY_SECRET="secret") were being hashed as part of the key string.
  • Fix: Added .replace(/['"]/g, '').trim() to sanitize environment variables upon loading (backend/routes/subscription.js line 10).
  • Regression Test: Unit test HMAC computation against Razorpay's official test vectors.
  • Prevention: Always sanitize and trim environment configuration strings on server startup.

Scenario 3: Google Sign-In Fails Silently on Android Device

  • Symptoms: User taps "Sign in with Google", selects their Google account, but the dialog dismisses and nothing happens.
  • Possible Causes: Missing SHA-1 / SHA-256 fingerprint in Firebase Project Console; mismatched OAuth Web Client ID in GoogleSignIn constructor.
